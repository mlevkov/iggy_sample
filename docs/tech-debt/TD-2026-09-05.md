# TD-2026-09-05: rust-cache is pinned to a branch head under a release comment

**Source:** Dependabot first-wave triage (2026-09-23), checking PR #37's
third-party SHA pins against their upstream tags. Carries the open part of
TD-2026-07-07's 2026-09-23 addendum.
**Status:** open

## Problem

TD-2026-07-07's convention is `uses: owner/action@<sha> # vX`, with the SHA a
release commit. `Swatinem/rust-cache` breaks it in all 17 of its uses (ci.yml
5, extended-tests.yml 6, pr.yml 3, release.yml 3): since PR #37 the pin is
`f0d9c388… # v2`, the head of upstream `master`, five commits past v2.9.2
(`6323deb`, where the `v2` tag points). Those commits are one fix (#377,
cleanup timestamp pruning) and two dependency bumps with their merges. The
comment says `v2`, but the SHA is no release. TD-2026-07-07's original pin,
`e18b4977…`, was not a release either: an untagged changelog commit made
three minutes before v2.9.1 was published.

For an untagged SHA, dependabot-core proposes the head of the branch that
contains it, which is how PR #37 arrived at `master`. So every github-actions
Dependabot PR can move rust-cache to whatever upstream merged last, under a
comment that names a release, and reviewing that means reading upstream
commits rather than release notes.

Two other pins track a branch deliberately, with comments that say so:
`dtolnay/rust-toolchain@… # master` (TD-2026-07-07's normalization) and
`rustsec/audit-check@858dc40f… # main`, three commits past v2.0.0 for its
Node 24 change. Upstream has published no audit-check release since v2.0.0
(2024-09-23); TD-2026-07-07's addendum left its return to a release SHA
open, and this record carries it.

## Mitigations in place

- The pins are still immutable SHAs in the upstream repositories. For PR #37
  each was compared with its tag or branch (`gh api
  repos/<owner>/<action>/compare/<ref>...<sha>`): softprops/action-gh-release,
  codecov/codecov-action and taiki-e/install-action are identical to their
  release tags, and dtolnay/rust-toolchain to `master`.
- rust-cache runs in most CI jobs, so a head that breaks it fails visibly.
  That says nothing about a head that misbehaves quietly.

## Proposed fix

- Re-pin rust-cache to v2.9.2's commit with an accurate comment,
  `Swatinem/rust-cache@6323deb102c322ba6fcbdcafc7e3dddab59af2b6 # v2.9.2`, in
  all 17 places. With a tagged SHA, Dependabot proposes releases from then
  on.
- Move audit-check to a release SHA the same way once upstream tags a
  release that includes its Node 24 change.

## Binding trigger

The next github-actions Dependabot PR that moves either pin. When it moves
audit-check, check upstream for a release after v2.0.0 then, since nothing
in this repository notices one on its own.
