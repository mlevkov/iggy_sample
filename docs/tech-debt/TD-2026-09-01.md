# TD-2026-09-01: API listener serves cleartext HTTP/2 by feature unification

**Source:** RUSTSEC-2026-0258 remediation (2026-09-22), exposure analysis for
the `h2` advisory.
**Status:** open

## Problem

The public API listener negotiates cleartext HTTP/2 (h2c, prior knowledge),
although nothing in this crate asks for HTTP/2:

- `Cargo.toml` adds only `macros` to axum's default features, which include
  `http1` but not `http2`. axum therefore never configures HTTP/2, but it never
  restricts it either: `axum::serve` hands every connection to a
  `hyper_util::server::conn::auto::Builder`.
- `metrics-exporter-prometheus`'s `http-listener` feature enables its
  `_hyper-server` feature, which enables `hyper-util/server-auto`, which implies
  `hyper-util/http2`. Feature unification builds a single `hyper-util` for the
  whole graph, so the HTTP/2 branch of the builder axum uses is compiled in and
  live. The exporter's own listener is `http1::Builder` only.

Verified on 2026-09-22 against `apache/iggy:0.8.0`:
`curl --http2-prior-knowledge http://127.0.0.1:$PORT/health` negotiates HTTP/2
and returns 200, while the same request to the metrics listener fails at the
HTTP/2 framing layer.

So an unrelated dependency's feature list decides the public listener's
protocol surface. It can appear or disappear on an exporter bump with no diff
in this crate, and it made RUSTSEC-2026-0258 reachable server-side while
`Cargo.toml` and the docs implied HTTP/1.1 only. The deployment guide's
reverse-proxy requirement narrows it in production (an HTTP/1.x upstream never
speaks h2c to the backend); the compose quick start and any directly exposed
port do not.

## Options

1. **Make HTTP/2 intentional.** Enable axum's `http2` feature, which also turns
   on the extended CONNECT protocol for HTTP/2 websockets, and document h2c
   support as a supported protocol.
2. **Restrict to HTTP/1.** axum 0.8's `Serve` exposes no builder configuration
   (only `with_graceful_shutdown` and `local_addr`), so this means replacing
   `axum::serve` in `main.rs` with an accept loop over
   `hyper::server::conn::http1` or `auto::Builder::http1_only()`. That loop
   must keep what the current call provides: graceful shutdown, and
   `ConnectInfo<SocketAddr>`, which the trusted-proxy gating in
   `src/middleware/ip.rs` depends on.

Either way, pin the choice with an integration test that sends an HTTP/2
prior-knowledge request and asserts the outcome, so a dependency bump cannot
silently flip it.

## Binding trigger

Whichever comes first: the next change to the HTTP serving path in `main.rs`,
the next `h2` advisory, or the next minor bump of `axum`, `hyper-util` or
`metrics-exporter-prometheus`.
