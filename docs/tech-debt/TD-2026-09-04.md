# TD-2026-09-04: The crates.io publish job cannot succeed

**Source:** Dependabot first-wave triage (2026-09-23), exercising release.yml
for PR #37's action bumps.
**Status:** open

## Problem

release.yml's publish job runs `cargo publish --token ${{
secrets.CRATES_IO_TOKEN }}` with `continue-on-error: true` after every stable
release. It cannot succeed, for two independent reasons:

- The repository has no `CRATES_IO_TOKEN` secret, so the command fails at
  argument parsing: `error: a value is required for '--token <TOKEN>' but
  none was supplied`. That is the failure in the publish step of all four
  stable releases, v0.2.0 through v0.4.1.
- With a token it would still fail: Cargo.toml sets `publish = false`, and
  cargo refuses before it uses the token (`` `iggy_sample` cannot be
  published ``, reproduced on 2026-09-23 with `--dry-run` and a dummy
  token). TD-2026-07-07 relies on that refusal as a mitigation.

`continue-on-error` hides the failure end to end. The job concludes success,
and the Actions API reports the failed step's conclusion as `success` as
well (checked on the v0.4.1 run, 35888419705), so the only trace is the
step's log line `##[error]Process completed with exit code 1.`. iggy_sample
is not on crates.io: the API returned 404 on 2026-09-23 (to a request with a
User-Agent; crates.io answers 403 without one).

## Mitigations in place

- Nothing can be published by accident: `publish = false` holds whatever
  the token.
- `scripts/verify-release.sh` fails a release whose step output has any
  `##[error]` line, including one under a job that concluded success, and
  `.github/workflows/verify-release.yml` runs it after every green Release
  run, so the next stable release fails that workflow instead of passing.
  Its first run (36068815000, 2026-09-24), which checked a re-run attempt
  of v0.4.1's Release run, failed on this step alone: 40 passed, 1 failed.
  The verifier also checks that crates.io lacks each version while
  `publish = false`.
- The publish job in release.yml and `publish = false` in Cargo.toml both
  name this record.

## Options

1. **Delete the job.** `publish = false` already says the crate is not meant
   for crates.io, so the job only adds a red step to every release and a
   secret reference that invites someone to configure a live token.
2. **Publish deliberately.** Set `publish = true`, add the token, and drop
   `continue-on-error` so a failed publish fails the release run.

## Binding trigger

Whichever comes first: the next stable release tag (the Verify Release
workflow fails on it until this is resolved), or the next edit to the
publish job or to `publish` in Cargo.toml.
