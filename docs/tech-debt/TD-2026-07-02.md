# TD-2026-07-02: DiagnosticEvents-driven connection state

**Source:** Review session 01, Round 1 — code-architect finding #2 (HIGH theme).
**Status:** open (mitigated; trigger fired 2026-09-18, due with the iggy 0.11 upgrade, which has to be done by hand)

## Problem

SDK 0.10's connection-string clients ship transport-level auto-reconnection
that cannot be disabled (`enabled: true` is hardcoded in
`TcpConnectionStringOptions::parse_options`) and that swallows most
mid-operation connection failures into blocking retries. The wrapper's view
of connection health is therefore indirect: bounded timeouts + periodic
`ping` probes (added in session 01). The SDK exposes a first-class signal we
do not consume: `Client::subscribe_events()` yields `DiagnosticEvent`
connect/disconnect notifications.

## Mitigation in place

`health_check()` live pings drive `ConnectionState` and the connection
gauge; timeouts are recorded as breaker failures; classified errors cover
the classes that escape the SDK's internal retry.

## Binding trigger

At the next iggy SDK minor bump, evaluate subscribing to `DiagnosticEvent`
to drive `ConnectionState`/breaker directly, and re-check whether the SDK
has made internal reconnection configurable from connection strings (if so,
decide once whether resilience policy lives in the SDK or the wrapper, and
delete the loser).

## Trigger check (session 02, 2026-07-05)

crates.io shows max stable `iggy` at **0.10.0** (newest is `0.10.1-edge.2`,
a pre-release, excluded by the trigger; Dependabot does not propose
pre-release upgrades from a stable version by default — note the
`version-update:semver-prerelease` entry in dependabot.yml is not among
GitHub's documented `ignore.update-types` values and is likely inert).
The "next SDK minor bump" trigger has NOT fired; the record stays open
and parked. Re-run the check at the next Dependabot `iggy` proposal.

## Trigger check (2026-09-23)

The trigger has FIRED: `iggy` 0.11.0 reached crates.io on 2026-09-18 as the
max stable version. It is outside Cargo.toml's `^0.10.0` requirement, so no
routine `cargo update` selects it, and it requires Rust 1.95, above this
crate's 1.93.0 MSRV, so the upgrade that makes this record due also forces an
MSRV raise. The MSRV is spelled out in six places: `Cargo.toml`, ci.yml's
`env.MSRV` (which no step reads) and its matrix literal, the README badge and
prerequisites, and CONTRIBUTING; the Dockerfile's toolchain has to stay at or
above it, which CI now checks.

Correction to the check above: the `version-update:semver-prerelease` entry
was not inert. It was one of two schema errors in a dependabot.yml that never
produced a Dependabot run or PR, until the RustSec 2026-09 remediation
repaired the file, so the "next Dependabot `iggy` proposal" could never have
arrived. With the config fixed, 0.11 should open as its own PR (Dependabot
counts a 0.x minor bump as major); whether Dependabot also holds it back for
the MSRV is untested, so if no PR appears, check the Dependabot run log. Treat
that PR as this record's work rather than a routine bump.

## Trigger check (2026-09-23, after Dependabot's first run)

No PR appeared: Dependabot's first cargo run opened #38-#42 and nothing for
`iggy`. Its log (Actions run 35888373353) shows both passes over the crate.
The grouped `rust-minor` pass saw `Latest version is 0.11.0` and left it
alone, as the group takes only minor and patch updates. The ungrouped pass,
the one that would have opened the PR, reported `Requirements to unlock
update_not_possible` and closed with `No update possible for iggy 0.10.0`,
its verdict when no newer version resolves; the log does not say why at
INFO level.

MSRV-aware resolution explains it, and reproduces locally (cargo 1.98.1).
Edition 2024 defaults to resolver 3, which prefers dependency versions whose
own `rust-version` fits this crate's 1.93.0. With the requirement loosened
to `iggy = ">=0.10.0"`, `cargo update -p iggy` locks 0 packages "to latest
Rust 1.93.0 compatible versions" and keeps 0.10.0; the same command with
`CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS=allow` moves `iggy`,
`iggy_common` and `iggy_binary_protocol` to 0.11.0. An exact
`iggy = "0.11.0"` also resolves, so the graph itself is satisfiable.

So Dependabot will not propose 0.11 while `rust-version` stays below 1.95. Do
this record's upgrade by hand, raising `rust-version` in the same change (the
six places above; that change also fires TD-2026-09-02). More generally,
Dependabot silently skips any update, security fixes included, whose new
version needs a newer Rust than `rust-version`; cargo-deny and cargo-audit
read the lockfile, so they still flag a vulnerable version that stays behind.
