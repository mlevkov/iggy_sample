# TD-2026-09-06: main accepts a pull request whose checks ran against an older main

**Source:** Dependabot first-wave triage (2026-09-23), merging PRs #37-#42.
**Status:** resolved (2026-11-07: ruleset updated)

## Problem

The `main` ruleset requires CI Success, Clippy, Integration Tests and Rustfmt
with `strict_required_status_checks_policy: false`, so a pull request whose
checks passed against an older main stays mergeable after main moves, and
GitHub's `MERGEABLE` means only that the diff still applies. Lockfile pull
requests are where that bites. After #38 (151 crates) merged, #39 (sha1) still
showed `MERGEABLE` with green checks computed on the pre-#38 lockfile, and
Dependabot never rebased it on its own: between scheduled runs it rebases a
pull request by itself only when it conflicts (it also rebases open pull
requests when its schedule runs, on reopen, and when the target branch
changes), and #39 never conflicted. Merging it as it stood would have put an
untested tree on main, with main's own CI as its first test, and ci.yml's
concurrency group cancels that run when the next merge lands, as it did for
#40's merge (`5a9054e`).

## Mitigations in place

The 2026-09-23 wave was merged under the strict rule by hand: `@dependabot
rebase` on each pull request that did not conflict, a merge only once the
head contained current main and every check on that head had passed, and
`gh pr merge --match-head-commit` so a later push could not slip in. That is
a procedure, not a gate.

## Proposed fix

Turn on "Require branches to be up to date before merging" in the main ruleset
(`strict_required_status_checks_policy: true`). A pull request behind main
then has to be updated before it merges; for a Dependabot pull request that is
`@dependabot rebase` and a fresh CI run. A merge queue would automate that
loop, but GitHub offers merge queues only to organization-owned repositories,
so for this user-owned one the setting above is the fix. Editing the ruleset
is an admin action.

## Binding trigger

Before merging the next Dependabot wave, that is, the next time two or more
open pull requests change Cargo.lock at once. Dependabot's next scheduled run
is Monday 2026-09-28 at 09:00 UTC.

## Resolution (2026-11-07)

The trigger fired when Dependabot opened #70-#73 at once, four pull requests
changing Cargo.lock. That wave was merged as one pull request (#75, the same
updates at the same versions and checksums) under the manual procedure above:
its head contained current main and every check on that head had passed
before `gh pr merge --match-head-commit`.

The maintainer then updated the `main` ruleset (ID 10646827) through the
REST API, changing only its `required_status_checks` rule:

- `strict_required_status_checks_policy: true`: a pull request behind main
  must be updated, and its checks rerun, before it can merge.
- `Dependabot Config` (PR Checks, TD-2026-09-02) joined CI Success, Clippy,
  Integration Tests and Rustfmt as a required check, pinned like them to the
  GitHub Actions app (`integration_id: 15368`).

What it costs: each merge leaves every other open pull request behind main.
Dependabot's need `@dependabot rebase`; others need main merged in. A
grouped Dependabot wave is still cheaper merged as one pull request, as #75
was.

What it does not cover: the ruleset's bypass actors. A merge with
`gh pr merge --admin` skips the up-to-date rule along with the review
requirement, so a bypass merge should still follow the procedure above.
