# ADR-0002: Move to Iggy server 0.10 / SDK 0.12 before the per-topic options PR

- **Status:** Accepted
- **Date:** 2026-11-07
- **Deciders:** Maxim Levkov
- **Amends:** [ADR-0001](0001-iggy-0.9-upgrade-and-demos.md) (PR sequence, PR 2–4 inputs, out-of-scope reasons)

## Context

ADR-0001 planned PRs 2–4 (per-topic options, clustering demo, connectors
demo) on server 0.9.0 and SDK 0.11.0. PR 1 merged that upgrade. On
2026-11-07, while PR 2 was starting, upstream released server 0.10.0, Rust
SDK 0.12.0 and connectors 0.6.0, all tagged on commit `91e02063`
([server-0.10.0](https://github.com/apache/iggy/releases/tag/server-0.10.0)).
The release blog post with upgrade notes is due 2026-11-09.

The following was verified on 2026-11-07, by type-checking this crate against
SDK 0.12.0, by running the integration suite against `apache/iggy:0.10.0`,
and by reading the SDK and server sources at `91e02063`.

### Compatibility

- **Wire:** SDK and server still move together, but a mismatch now fails
  fast in both directions:
  - SDK 0.11 against server 0.10 fails sign-in with "Incompatible binary
    protocol version: client 0.11.0, server accepts [0.12.2, 0.12.2]". The
    existing `IncompatibleServer` path ends startup with `EX_PROTOCOL`.
  - SDK 0.12 against server 0.9 fails sign-in with "Invalid format".
- **Data:** 0.10 refuses a 0.9 data directory: "storage at /iggy/data does
  not match this build's storage format; startup refused without modifying
  data. No in-place upgrade is supported". This contradicts the config
  file's superblock note (version 1 records "remain readable"), which covers
  only the consensus superblock, not the storage format.
- **Compile break:** three call sites.
  - `create_stream` takes `&StreamCreateOptions`.
  - `poll_messages` takes `partition_id: u32` and a `PollOptions` (count,
    byte cap, `CommitPolicy`) instead of `Option<u32>`, a count and an
    auto-commit flag.
  - `send_messages` now returns a `SendMessagesResponse` with per-partition
    confirmations.

### Server behaviour

- **NUMA:** 0.10 skips NUMA memory binding on a single-node host
  (apache/iggy#4243). The default `numa:auto` boots on Docker Desktop, so the
  `IGGY_SHARDING_CPU_ALLOCATION=all` workaround from ADR-0001 is no longer
  needed. 0.9 still aborts without it.
- **WebSocket:** the WebSocket listener is on by default, bound to loopback,
  and 0.10 warns about a loopback bind inside a container.
- **Unchanged here:** the readiness log line ("server HTTP listener
  started"), the advertised-address requirement for wildcard binds, the
  bearer credential on `/metrics`, and the embedded Web UI.

### SDK 0.12 lanes

SDK 0.12 admits one mutation at a time per *lane*: one lane for metadata and
one per partition, plus a progress lane per partition for auto-commit and
`Next` polls. A mutation whose outcome the SDK cannot prove stays *retained*
in its lane. Every later call on the lane then fails with `LaneBlocked` (or
`PartitionLaneBlocked`) until the application calls `resolve_operation` or
`abandon_operation`. The SDK's own `IggyProducer` does this; the trait-level
API this gateway uses leaves it to the caller.

Two paths retain an operation:

- the call returns `OperationUncertain(op)` or `FetchProgressUncertain(op)`;
- the call is dropped after its request left the client, and nothing names
  `op`.

The gateway's per-request timeout drops calls that way. Reproduced against
server 0.10.0 with a frozen container: after one timed-out send, the next
send to that partition failed with "Lane blocked by operation 12 with an
unknown outcome". It would go on failing for the life of the client.

### Diagnostic events

SDK 0.12 publishes `Disconnected` as soon as the last link closes, while it
goes on redialling. SDK 0.11 published it only when a bounded reconnect
sweep gave up, which never happens with the connection strings' default
unlimited retries. The integration test for loss events now passes with
that default.

### Inputs to PRs 2–4

- **PR 2 (topic options):**
  - the create-side fields ADR-0001 lists carry over unchanged;
  - 0.12 adds `partition_resize_policy` and `replication_factor`;
  - topics are read back with *resolved* options that mark each value as
    explicit or a server default;
  - topics can be patched with typed `TopicUpdateOptions`.
- **PR 3 (clustering):**
  - topics carry a per-topic replication factor, and the server-wide
    `default_replication_factor` is `"all"`. ADR-0001's "every partition
    lives on every node" holds only for that default;
  - HTTP sends, polls and offset calls that reach a node that is not the
    partition primary answer a transient 503 (code 58);
  - mixed-version clusters cannot sustain a primary's quorum checks, so
    nodes upgrade together.
- **PR 4 (connectors):**
  - connectors 0.6.0 is tagged on `91e02063`;
  - `apache/iggy-connect:0.6.0` is published;
  - the release includes the HTTP source fix apache/iggy#4302.
- **Out-of-scope reasons in ADR-0001 that no longer hold:**
  - the Kafka gateway now answers Produce, Fetch, ListOffsets and consumer
    group calls;
  - deferred polling is released (`PollOptions::max_wait`).

## Decision

1. **Insert PR 1b, `feat/iggy-0.10`, before PR 2:**
   - server 0.10.0 and SDK 0.12.0;
   - the three call-site changes;
   - a new compose data volume, `iggy_data_0_10`;
   - compose and fixture changes: the NUMA workaround removed and the
     WebSocket listener disabled.
2. **Settle lanes in the wrapper.** Every lane-taking SDK call (sends,
   creates, deletes, polls) goes through `lanes::settled` /
   `lanes::send_settled`:
   - an operation named by `OperationUncertain`, `FetchProgressUncertain`,
     `LaneBlocked` or `PartitionLaneBlocked` is abandoned;
   - a lane-refused call runs once more, since a refusal takes no request
     id and so nothing was sent;
   - the gateway never resolves or resends an unknown outcome itself.
     Abandoning leaves that outcome unknown, which is what the earlier HTTP
     caller was told.
3. **Classify the new outcomes:**

   | Error | Gateway response |
   |---|---|
   | `OperationUncertain`, `FetchProgressUncertain`, `RequestTooOld` | `OutcomeUnknown` (503, not retried) |
   | `LaneBlocked`, `PartitionLaneBlocked`, `LifecycleBusy` | `NotAccepted` (retryable 503) |

4. **Auto-commit polls use `CommitPolicy::OnRead`,** the 0.12 equivalent:
   the server stores the offset of the last message as part of the read.
   The poll byte cap stays at the SDK default of 1 MiB.
5. **PR 2 builds on SDK 0.12:**
   - it keeps ADR-0001's field list;
   - it reports resolved options, with their provenance, on topic `GET`;
   - `replication_factor` moves to PR 3, where a cluster gives it meaning;
   - topic updates stay out of PR 2.
6. **PR 3** demonstrates the per-topic replication factor alongside the
   default `"all"`.
7. **PR 4** pins `91e02063` and `apache/iggy-connect:0.6.0` instead of
   `71f29618` and 0.5.0.
8. **Still out of scope:** the Kafka gateway and deferred polling stay out
   of this sequence. Their ADR-0001 reasons are gone, but this repository
   demonstrates the Iggy-native API, and each needs its own decision.

## Alternatives considered

- **PR 2 on SDK 0.11, upgrade afterwards.** Rejected: topic read-back and
  the storage guide would be written for 0.11 and redone for 0.12, and the
  lane hazard would wait until the upgrade.
- **Wait for the upgrade notes (2026-11-09) and an early patch release.**
  Rejected: the facts that matter here were verified directly. The notes
  will be checked against this record when they appear.
- **Resolve retained operations in the background instead of abandoning
  them.** Rejected: the HTTP caller has already been answered, so a proved
  outcome has nobody to go to, and a background resolve holds the lane while
  it runs.
- **Use `IggyProducer`, which settles lanes itself.** Rejected for the
  reasons in CLAUDE.md: it binds to one stream and topic at build time,
  while this gateway serves arbitrary per-request routes.

## Consequences

- Anyone running the compose stack starts on an empty `iggy_data_0_10`
  volume. The old `iggy_data_0_9` can be removed.
- A poll returns at most about 1 MiB of messages, so a large `count` can
  return fewer messages than before. `current_offset` says where to resume.
- A lane refusal costs one extra SDK call, and an unknown outcome one extra
  abandon. Neither sends anything to the server.
- With the default unlimited retries, `/health` and `/ready` now drop as soon
  as the connection closes, instead of at the next health-check ping.
- The SDK serialises mutations per lane for each client, so concurrent sends
  to one partition from this gateway queue inside the SDK. A lane still busy
  at the request deadline answers `TransientNotAccepted` (retryable 503).
