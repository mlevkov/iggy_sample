# ADR-0001: Upgrade to Iggy server 0.9 / SDK 0.11, and add clustering and connector demos

- **Status:** Accepted; amended by [ADR-0002](0002-iggy-0.10-before-topic-options.md) (2026-11-07)
- **Date:** 2026-11-06
- **Deciders:** Maxim Levkov

## Context

This repository runs Iggy server 0.8.0 with Rust SDK 0.10.0. On 2026-09-18,
upstream released server 0.9.0 with Rust SDK 0.11.0 and connectors 0.5.0, all
tagged on commit `71f29618`. The release notes are in the
[blog post](https://iggy.apache.org/blogs/2026/09/21/release-0.9.0) and at
[server-0.9.0](https://github.com/apache/iggy/releases/tag/server-0.9.0).
Several facts constrain the upgrade.

### The upgrade is lockstep and one-way

- VSR framing is the only binary wire protocol, so 0.8 clients cannot talk to
  a 0.9 server.
- 0.8 data directories are not migrated.
- SDK 0.11 needs Rust 1.95, above this crate's `rust-version` of 1.93. Cargo's
  MSRV-aware resolver keeps Dependabot from proposing it (TD-2026-07-02), so
  the bump is done by hand.

### Server behaviour changes the compose file and tests depend on

These were verified on 2026-11-06 by running the integration suite against
`apache/iggy:0.9.0` in a throwaway worktree. With the changes below, all 31
tests pass.

- **Boot is refused on a wildcard bind** (`0.0.0.0`) unless
  `IGGY_NODE_ADVERTISED_ADDRESS` is set.
- **The default `sharding.cpu_allocation = "numa:auto"` aborts on Docker
  Desktop** ("failed to bind shard memory to its NUMA node"), so it needs
  `IGGY_SHARDING_CPU_ALLOCATION=all`.
- **The published image's listeners default to loopback**, so every address
  must be set to `0.0.0.0` explicitly.
- **The startup log line changed.** "Iggy server is running" is gone; the tests
  now wait for "server HTTP listener started".
- **`/metrics` requires a bearer credential** (a JWT or a personal access
  token, PAT). Without one it answers `401 access_token_missing`.
- **The data path moved.** The image's working directory is `/app` and the
  default `path` is `local_data`, so data lands in `/app/local_data`.
  `docker-compose.yaml` mounts `/iggy/data`, which misses it.
- **Config was reorganised.** `[system]` is flattened, so the `IGGY_SYSTEM_*`
  variables lose `SYSTEM_`. `enforce_fsync` is rejected. Segment and flush
  settings moved to per-topic options. `docs/durable-storage-guide.md` is
  wrong for 0.9 as a result.

### SDK 0.11 API changes

- `create_topic` takes a single `&TopicCreateOptions`. It was the only compile
  break in this crate.
- New error variants:

  | Variant (code) | Meaning |
  |---|---|
  | `TransientNotCommitted` (57) | The outcome is unknown. The SDK replays it on the same session for up to 30 s. |
  | `TransientNotAccepted` (58) | The request was never admitted, so a retry is safe. |
  | `RequestAlreadyApplied` (59) | The write happened, but its reply is gone. |
  | `IncompatibleProtocolVersion` | The client and server protocol versions do not match. |

  All four currently fall through to a generic 500 in
  `src/iggy_client/helpers.rs`.
- Connection-string reconnection is still hard-wired to `enabled: true`
  (`tcp_connection_string_options.rs`).
- `Client::subscribe_events()` still yields
  `Connected`/`Disconnected`/`SignedIn`/`SignedOut`/`Shutdown`.

### Clustering (VSR) is in the standard server binary, off by default

- The roster is static and uses literal IPs, so containers need fixed
  addresses.
- Each node needs its own data volume, plus a shared secret of at least 32
  bytes.
- Replica count equals roster size, so every partition lives on every node.
- The SDK takes **one** seed address and learns the rest from cluster
  metadata. It follows the leader (at most 3 redirects, a 5 s leaderless
  wait) and fails over between roster nodes.
- Auto-commit polls and offset stores are routed to the partition primary
  over extra connections, so the client must be able to reach every node's
  advertised address.
- A follower's HTTP listener forwards writes rather than redirecting them.
- Membership changes and partition reassignment are not documented (treated
  as unsupported).

### Connectors

- **The runtime image ships no plugins.** `apache/iggy-connect:0.5.0` contains
  only the runtime binary; plugin `.so` files are built from source
  (`publish = false`, no release assets).
- **The HTTP source is a webhook receiver**, not a URL poller:
  - It accepts `POST /topics/{topic}` and secret-path `POST /e/{endpoint_id}`
    with bearer or HMAC-SHA256/SHA1 auth.
  - It requires `schema = "raw"`.
  - It only writes to topics with `durability = persisted`.
  - A 200 response means only that the body was buffered in memory.
- **The HTTP sink POSTs topic messages to one URL**:
  - Batching modes: individual, `ndjson`, `json_array`, `raw`.
  - It retries with backoff on 429 and 5xx.
  - It commits offsets *before* delivery, so it is at-most-once.

## Decision

The work is delivered as the following sequence of pull requests. Each one
leaves `main` green and stands alone.

| # | Branch | Scope |
|---|---|---|
| 0 | (dependency upkeep) | Merge #61 (Actions bumps) after #65 (accept dev-only RUSTSEC-2026-0440). Then re-pin `Swatinem/rust-cache` to the v2.9.3 release SHA (TD-2026-09-05). |
| 1 | `feat/iggy-0.9` | The core upgrade, below |
| 2 | `feat/topic-options` | Per-topic options and the storage guide rewrite, below |
| 3 | `feat/cluster-demo` | Clustering demo, below |
| 4 | `feat/connectors-demo` | HTTP source and sink demo, below |
| — | (follow-up to #64) | Refuse to start when `API_KEY` is set without `TRUSTED_PROXIES`, with an explicit opt-out for local development |

### PR 1: core upgrade

- SDK 0.11.0 and server 0.9.0.
- `rust-version` 1.95 in all six places it is declared, plus the Dockerfile
  toolchain. This fires TD-2026-09-02.
- `create_topic` moves to `TopicCreateOptions`.
- Compose and test-fixture changes:
  - advertised address and CPU allocation;
  - explicit binds;
  - the data volume at `/app/local_data`;
  - `cap_add: SYS_NICE`, `seccomp:unconfined` and an unlimited memlock limit
    instead of `privileged`;
  - the new readiness log line.
- Prometheus scrapes `/metrics` with a PAT. A one-shot init container creates
  it (`iggy pat create`) and writes it to a shared volume; Prometheus reads it
  through `authorization.credentials_file`.
- The embedded Web UI (`IGGY_HTTP_WEB_UI=true`) replaces the separate
  `iggy-web-ui` container, but only if the published image contains it;
  otherwise the container stays.
- Error classification:

  | Error (code) | Gateway response |
  |---|---|
  | 58 `TransientNotAccepted` | Retryable 503 |
  | 57 `TransientNotCommitted` | 503 that says the outcome is unknown. The wrapper's single retry is **not** used, because a resend could duplicate messages. |
  | 59 `RequestAlreadyApplied` on a send | **202 Accepted** with a body saying the write was applied but its reply is unavailable, so clients do not resend. |
  | `IncompatibleProtocolVersion` | Fail startup with a clear message. |

- TD-2026-07-02 is resolved this way:
  - Subscribe to `subscribe_events()` so `ConnectionState` and the connection
    gauge update immediately instead of waiting up to 30 s for a ping.
  - Keep the ping as a backstop.
  - Keep the wrapper's resilience layer, since SDK reconnection cannot be
    disabled from a connection string.

### PR 2: per-topic options

- `POST /streams/{s}/topics` accepts optional `durability`,
  `consumer_offset_durability`, `message_expiry`, `max_topic_size`,
  `segment_size`, `messages_required_to_save`,
  `size_of_messages_required_to_save` and `preallocate_segments`.
- The default topic takes the same settings from environment variables.
- Topic `GET` responses report them.
- `compression` is left out because the server does not apply it yet.
- `docs/durable-storage-guide.md` is rewritten around per-topic durability.

### PR 3: clustering demo

- **`docker-compose.cluster.yaml`:**
  - three nodes on a fixed subnet;
  - the full roster shared through a YAML anchor;
  - one volume per node;
  - the cluster secret taken from `.env`;
  - the gateway inside the compose network. Whether container IPs are
    reachable from a macOS host is unverified, so the demo does not depend on
    it.
- **Gateway additions:**
  - try an ordered list of seed addresses at startup, covering the SDK's
    single-seed limit;
  - `GET /cluster`, which reports node roles and health from cluster metadata.
- **`scripts/cluster-failover-demo.sh`** drives steady traffic, kills the
  leader, and shows roles change and traffic resume. Upstream's own test
  allows the first send after the kill to fail.
- **A 3-node test** runs in the weekly extended-tests workflow, not on every
  PR. This repository is public, so the self-hosted runner is not used.

### PR 4: connectors demo

- **`connectors/Dockerfile`** builds `iggy_connector_http_source` and
  `iggy_connector_http_sink` from apache/iggy at the pinned release commit
  `71f29618`, then copies them onto `apache/iggy-connect:0.5.0`. The build
  stage must stay glibc/Debian trixie to match the runtime image.
- **Inbound flow:** an external system POSTs an HMAC-SHA256 signed webhook to
  the HTTP source. It lands in a `persisted` `webhooks` topic and is readable
  through the gateway's existing poll API.
- **Outbound flow:** a gateway `POST /messages` goes to `events`, and the HTTP
  sink POSTs batched NDJSON to a **receiver endpoint in the gateway**
  (`POST /sink/inbound`). The loop closes inside this repository and can be
  tested end to end without a third-party image.
- **Connectors runtime:**
  - it authenticates to Iggy with the PAT from PR 1;
  - its Prometheus metrics are scraped and shown in Grafana.
- **The documentation states the delivery semantics plainly:**
  - the sink is at-most-once;
  - a source 200 means buffered in memory, best-effort, and duplicates are
    possible.

### Out of scope

- The Kafka gateway: in 0.9.0, `Produce`/`Fetch`/`ListOffsets` return
  retriable errors.
- Deferred polling, which is not released.
- Edge pre-releases (0.9.1-edge / 0.11.1-edge).
- HTTPS on Iggy's REST listener.
- Connectors other than HTTP.
- Message encryption is documented only (a one-line `[encryption]` config),
  not demonstrated.
- The high-level `IggyProducer`/`IggyConsumer` clients stay unused. The
  gateway serves arbitrary per-request routes, as CLAUDE.md explains.

## Alternatives considered

- **One upgrade PR with everything.** Rejected: the API change and the guide
  rewrite would make PR 1 too large to review well.
- **Separate echo container as the sink's target.** Rejected: it adds a
  third-party image and leaves the loop untestable inside the repository.
- **Waiting for upstream to publish connector plugins.** Rejected: no
  published plugins exist, and nothing upstream says any are planned.
- **Pinning the edge line (0.9.1-edge.x).** Rejected: it is a pre-release, and
  the demo should track stable.

## Consequences

**Upgrade and runtime:**
- Anyone running the compose stack must discard the old `iggy_data` volume.
  0.9 cannot read 0.8 data.
- The minimum supported Rust becomes 1.95. Dependabot can then propose SDK
  updates again.
- The test fixture and compose file carry three server settings (advertised
  address, CPU allocation, binds) that were defaults before.
- Prometheus depends on a token-provisioning step. If it fails, the server
  metrics panels go blank, so the init container must fail loudly.

**Demos:**
- The connectors image takes a long first build (it compiles the plugins) and
  is pinned to one upstream commit. Bumping connectors means changing that pin
  deliberately.
- The cluster demo demonstrates failover, not elasticity: the roster is
  static.

**Gateway API:**
- Error 59 on a send now returns 202. That is a documented change in API
  behaviour.
